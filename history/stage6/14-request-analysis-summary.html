요청 분석과 다른 판 검색

이슈 #14 · 2026-10-26 ~ 2026-10-27

앞 단계에서 한 것: 이슈 #13에서 Agent-RAG의 흐름을 PDF의 두 고리로 한 장에 그리고, 요청 분석과 1단계 고리부터 붙이기로 정했다. 그래서 이 단계: 1단계 고리를 만들어 질문 38개로 190번 재고, 효과가 있는 칸만 남겼다.

이 이슈는 처음에 두 기능을 차례로 붙이는 서브이슈였다. 하나는 요청 분석과 1단계 고리(검색하기 전에 검색 계획을 쓰고 검사·고치기)이고, 다른 하나는 도구 호출 검색(모델이 검색 도구를 스스로 부름)이다. 재 보니 검색 계획의 한국어판·영어판으로도 검색하는 "다른 판 검색"은 효과가 있어 남겼다. 계획을 검사하는 저지먼트와 고치는 리파이먼트는 결과를 하나도 바꾸지 못하고 계획을 망가뜨려 뺐다. 도구 호출 검색은 첫 검색에서 모델이 고를 것이 없어 따로 만들지 않고, 충분성 판단과 재검색을 붙일 때 함께 붙이기로 했다. 실행 기록에 시간 세 가지를 남기는 틀도 이 이슈에서 넣었다.

결과물은 코드(src/agent/), 190번 실행 기록과 견주기 요약(data/agent/plan_search/), 확대 페이지(history/stage6/14-request-analysis-search.html), 전체 그림의 표시다. 이 글은 확대 페이지와 다른 파일이다. 확대 페이지는 정할 것을 하나씩 정하던 자리이고, 이 글은 그 흐름을 다시 보는 글이다. 항목 번호는 이슈 체크리스트의 차례(1~11)다.

흐름

01검색 계획과 재는 법

사용자 지적항목 2: 원래 질문, 한국어판, 영어판 세 개로 검색한다생성 모델이 질문 전체의 한국어판과 영어판을 하나씩 쓰고, 코드는 원래 질문까지 세 글로 검색한다. 질문의 언어를 가리는 규칙은 두지 않는다.
바뀐 것
처음에는 요청 분석과 계획 쓰기를 요청 몇 번으로 할지부터 정했다. 사용자가 지금 시스템이 실제로 무엇을 가져왔는지 보지 않고 정했다며 설계를 처음부터 다시 하자고 해 그 결정을 거뒀다. 다시 정할 때 검색어의 꼴은 처음에 "질문 전체를 다른 언어로 옮긴 것 하나와 원래 질문"이었다. 그러면 코드가 질문의 언어를 가려야 해서 "두 판을 다 쓰고 원래 질문까지 세 개"로 바꿨다.
정한 것
검색 계획의 칸은 찾을 것 목록(사실마다 조건과 단위), 한국어판, 영어판이다. 요청은 한 번이다. 질문이 이미 그 언어면 그대로 옮겨 쓴다.
이유
지금 시스템이 놓친 영어 질문 5개 가운데 4개(q03, q09, q13, q14)는 사람이 써 둔 한국어 짝 질문을 같은 검색에 넣으면 근거 청크가 1등이나 2등이었다. 근거가 한국어 문서에만 있던 질문이다.
버린 것
찾을 것만 짧게 검색어로 쓰는 안(예: "이트륨 밀도")은 질문의 조건이 빠진다. 찾을 것과 질문 전체를 둘 다 쓰는 안은 검색이 네 번으로 늘어난다.

예영어 질문 q03-en(이트륨 직육면체의 질량)은 한국어판 "이트륨 직육면체의 질량은"으로도 검색해, 한국어 문서에만 있는 이트륨 밀도 청크를 가져온다.

항목 5: 원래 질문의 8개를 모두 두고 다른 판의 위쪽 4개씩을 더한다답 쓰기로 넘기는 청크는 원래 질문 검색의 8개에, 한국어판과 영어판 검색의 위쪽 4개씩을 겹치지 않게 더한 것이다. 이 목록이 "첫 검색의 청크"다.
정한 것
한국어판이나 영어판이 원래 질문과 글자가 같으면 그 판의 검색은 하지 않는다. 그래서 대개 검색 두 번, 청크 8~12개다.
이유
원래 질문의 8개를 다 두면 지금 시스템이 찾던 근거를 잃지 않는다. 더하는 수 4는 지금 가져오는 수 8의 절반이라는 원칙으로 정했고, 결과를 보고 고르지 않았다.
버린 것
순위 점수를 더하는 안은 원래 질문과 같은 언어판이 거의 같은 글이라 그 언어의 청크가 점수를 두 번 받는다. 그러면 다른 언어판에서만 1등인 근거 청크가 밀려, q03-en에서 근거가 빠졌다. 번갈아 8개를 고르는 안은 원래 질문 목록의 위쪽 4개만 들어가 지금 시스템이 5등에서 찾던 근거 3개를 잃을 수 있다.
한계
더한 청크가 원래 질문 검색의 9등 이하에 있던 근거의 자리를 차지할 수 있다. 실제로 q12-ko에서 그렇게 됐다(아래 묶음 2).
Codex 지적항목 5, 6: 같은 수의 청크를 원래 질문으로 가져온 비교용과 견준다새 시스템이 비교용보다 근거를 11번 이상 더 찾으면 다른 판 검색을 남긴다. 비교용은 실행마다 새 시스템이 넘긴 수만큼 원래 질문 검색의 위에서부터 가져온다.
바뀐 것
처음에는 비교용을 늘 12개로 두었다. Codex 설계 검토 1차가 새 시스템의 청크 수는 겹침 때문에 8~16개로 바뀌어 12개 고정으로는 효과를 가를 수 없다고 짚어, 실행마다 수를 맞추게 바꿨다.
정한 것
10번 이하로 많으면 사람이 옮긴 짝 질문으로 같은 방식의 검색을 해 원인을 가른다. 짝 질문으로도 비교용보다 11번 이상 많지 않으면 뺀다. 계획 검사와 고치기를 남길지를 먼저 정하고, 그 결과로 어느 계획으로 셀지 정한 뒤 다른 판 검색을 판단한다.
이유
비교용과 새 시스템은 넘기는 청크 수가 같고 더 얹는 청크를 어디서 가져오느냐만 다르다. 새 시스템이 비교용만큼만 찾으면 청크를 더 가져오기만 해도 된다는 뜻이다. 10번은 질문 2개 × 씨앗 5개로, 5단계 검색 조합 고르기의 선을 옮겼다.
한계
짝 질문으로 검색은 사람이 옮긴 한 가지 판으로 본 값이고, 번역을 고쳐 얻을 수 있는 가장 높은 값이 아니다(Codex 2차 설계 검토로 말을 좁힘).

02재 보고 판단한 것

사용자 지적항목 7: 계획 쓰기는 온도 0으로 한다검색 계획을 쓰는 요청만 온도 0으로 바꿨다. 답 쓰기는 0.7 그대로다.
바뀐 것
처음에는 계획 쓰기도 답 쓰기와 같은 온도 0.7이었다. 세 번째 190번에서 판정 모델이 같은 말을 되풀이하다 끊겨 꼴 오류가 났고, AI는 처음에 시험 없이 모델의 한계로 보았다. 사용자가 멈춘 이유를 제대로 분석해서 고쳐야 하지 않느냐고 해 시험했다.
정한 것
계획 쓰기의 나머지 설정은 답 쓰기와 같고 온도만 0이다.
이유
시험에서 q01-ko의 한국어판을 원문 그대로 옮긴 것은 온도 0에서 10번 가운데 10번, 0.7에서 6번이었다. JSON 꼴 강제는 켜든 끄든 5번 가운데 3번이라 원인이 아니었다. 0.7은 "유로퓸" 같은 드문 낱말을 깨뜨렸다(원본 출력: research_notes/stage6_plan_tests/plan_temperature/).
한계
온도 0에서도 q09-ko("어븀"을 "어铒"로), q18-ko(사람 이름을 한글로), q19-ko("(Studsvik)"을 뺌)는 원문과 다르게 옮겼다. 그 때문에 근거를 잃은 실행은 없었고, 정해 둔 규칙대로 지금 고치지 않고 기록만 했다. 온도 0이라 씨앗 5개가 같은 계획을 내, 계획 쪽은 사실상 질문 38개로 잰 셈이다.
항목 7: 다른 판 검색은 남긴다새 시스템 175 빼기 비교용 160은 15로, 정해 둔 선 11을 넘었다. 맞은 답은 144에서 167로 늘었다.
정한 것
다른 판 검색을 남긴다. 번역 실수는 고치지 않고 기록만 한다.
이유
얻은 질문은 근거가 한국어 문서에만 있던 영어 질문 넷(q03-en, q09-en, q13-en, q14-en)으로, 5번 모두 못 찾다가 5번 모두 찾았다. 근거를 찾은 실행 가운데 맞은 답은 167/175로, 지금 시스템(144/155)보다 낮지 않았다.
한계
q12-ko는 비교용이 5번 모두 찾았는데 새 시스템은 0번이었다. 근거가 원래 질문 검색의 9번째 청크에 있었는데 그 자리를 다른 판 청크가 차지했다. 그래서 15는 질문 3개 몫(얻음 4, 잃음 1)이다.
사용자 지적항목 7: 저지먼트와 리파이먼트를 뺀다계획을 검사하는 저지먼트와 고치는 리파이먼트는 결과를 하나도 바꾸지 못하고 계획을 망가뜨려 뺐다. 생성이 처음 쓴 계획으로 바로 검색한다.
정한 것
1단계 고리는 생성 하나만 남는다. 판정 모델의 지시문과 고치기 요청 글의 전문은 결정 파일에만 남는다.
이유
이번 기록에서 계획을 다시 쓴 실행은 10번(q09-ko, q14-ko)이고 근거와 답이 바뀐 실행은 0번이었다. 앞 기록까지 합쳐도 견줄 수 있는 67번에서 0번이었다. 판정 지시문을 고친 판과 생성 모델의 생각 과정을 보여 준 판으로 계획 8개(틀린 5, 맞는 3)를 다시 판정시켜도 8개 가운데 2~3개만 바르게 판정했다.
과정
처음에는 AI가 고친 지시문 하나로 두 질문만 시험했다. 사용자가 그 지시문이 무조건 맞다고 할 수는 없지 않느냐고 해, 지시문 네 가지와 계획 여덟 개로 넓혔다.
버린 것
판정 모델을 바꾸는 안은 모델을 고르는 결정이라 이 이슈의 범위 밖이었다. 바꾸면 나아질지는 확인하지 않았다.
한계
시험한 지시문은 AI가 쓴 몇 개뿐이라 "이 모델로는 안 된다"를 증명하지 않는다. 질문 38개 대부분은 원래 질문만으로도 근거를 찾아(155/190) 이 칸이 효과를 보일 자리가 적었다.

예q09-ko(어븀 직육면체의 질량)가 칸을 지나간 길이다. 1단계 생성(LLM)이 "어븀"을 "어铒"로 깨뜨렸다. 저지먼트(LLM, 판정 모델)는 그것을 못 찾고 맞는 곳을 틀렸다고 했다. 리파이먼트(코드)가 지적을 모아 생성으로 돌려보내자, 두 번째 저지먼트가 "어铒를 어뢰로 바꿔라"라고 없는 잘못을 지어냈고 생성이 그대로 따랐다. 영어판은 "sonar rectangular prism"(음파 탐지기 직육면체)이 되었고, 세 번째 저지먼트가 통과시켰다. 원래 질문 검색의 8개에 근거가 있어 결과는 바뀌지 않았다.

03시간 기록과 도구 호출 검색의 자리

사용자 지적항목 8: 모든 기능에 시간 세 가지를 남긴다실행 전체 시간, 칸마다 시작과 끝, 모델 요청마다 읽기, 쓰기, 모델 올리기 시간을 실행 기록에 남긴다. 뒤에 붙이는 기능도 같은 두 길을 지나가게 한다.
정한 것
넣는 곳은 모든 모델 요청이 지나가는 요청 함수(send)와, 그래프에 칸을 붙일 때 감싸는 함수 하나(timed)다. 바깥으로 기록을 보내는 추적 기능은 쓰지 않는다.
이유
190번 실행 중 답 쓰기가 최소판의 가운데값 5.8초에서 약 10초로 느려졌는데, 그때 기록으로는 읽기, 쓰기, 모델 올리기 가운데 어디서 늘었는지 가를 수 없었다. 사용자는 기능을 붙일 때마다 칸과 칸 사이에 얼마나 걸리는지 흐름 전체를 보고 싶다고 했다.

예넣은 뒤 짧은 실행에서 q01-ko는 실행 21.2초 가운데 생성 9.0초, 검색 0.3초, 답 쓰기 11.9초였고, 답 쓰기의 읽기가 4.9초였다.

사용자 지적항목 8, 9, 10: 도구 호출 검색은 충분성 판단과 재검색을 붙일 때 함께 붙인다첫 검색은 검색어가 1단계 계획으로 이미 정해져 있어, 모델에게 검색 도구를 부르게 해도 같은 세 검색어로 같은 검색을 할 뿐이다. 그래서 도구 호출 검색을 따로 만들지 않는다.
바뀐 것
처음 계획은 이 이슈에서 도구 호출 검색을 만들고 190번 재는 것이었다. 시험에서 "필요한 만큼 검색하라"고 하면 모델이 5개 질문 모두 영어로만 검색했고, "계획대로 세 번 검색하라"고 하면 5개 모두 한국어판으로 검색했다. 그래서 "계획대로"로 정했는데, 사용자가 그러면 이전과 다른 게 무엇이냐, 모델이 고르는 것은 툴유즈가 아니라 저지먼트와 리파이먼트에서 일어나지 않느냐고 짚었다. 첫 검색에서는 모델이 고를 것이 없다는 것이 드러나 충분성 판단과 함께 붙이기로 바꿨다.
정한 것
붙이는 순서는 요청 분석, 답변 합성, (개발용 질문으로 다시 돌림), 충분성 판단과 재검색(도구 호출 검색을 품음), 판정, 답 고치기, API다.
이유
전체 그림의 칸마다 LLM이 붙는 곳을 보면, 지금은 1단계 생성과 답 쓰기만 LLM이고 2단계 생성(검색어 고르기), 툴유즈(검색 도구 호출), 관찰값은 코드다. 툴유즈는 어느 기능에서도 받은 검색어로 벡터 검색을 하는 코드다. 2단계 생성의 LLM이 고를 일이 생기는 것은 저지먼트(충분성)가 모자라다고 보아 새 검색어를 써야 할 때다.
한계
도구 호출 검색의 완료 기준(모델이 도구를 부름, 같은 인자면 5단계와 같은 청크, 문서는 도구로만)은 이 이슈에서 채우지 않았고 미정 목록의 충분성 판단 줄로 넘겼다. 그때 첫 검색은 같은 질문으로 잰 이번 결과보다 근거를 1번이라도 덜 찾으면 원인을 찾는다(사용자: "그래도 나빠지지 않으면 안되는거 아닌가 싶은데").

세부로 정한 것

  • 항목 4: LangGraph를 고른 주된 까닭은 사용자가 공부한 프레임워크가 LangChain과 LangGraph뿐이었던 것이다. 설계해 보니 고리와 횟수 한도를 칸과 갈라지는 화살표로 그대로 옮길 수 있었다.
  • 항목 3: 계획 검사는 최대 3번, 끝내 떨어지면 마지막 계획으로 검색한다. 항목 7에서 검사와 고치기를 빼면서 쓰지 않게 됐다.
  • 항목 6: 리파이먼트는 참고 PDF의 고리대로 지적을 모아 생성으로 돌려보내는 칸으로 되돌렸다(사용자 지적).
  • 항목 6: 고치기가 일어난 실행에서는 처음 계획으로도 검색하고 답을 써 채점해 두었다. 그래서 검사와 고치기를 뺄 때 다시 돌리지 않고 셀 수 있었다(Codex 지적).
  • 항목 6: 모델 답의 꼴을 코드가 검사하고, 꼴 오류가 난 실행은 검색 전에 멈추며 견주는 프로그램은 꼴 오류가 하나라도 있으면 값을 내지 않는다(Codex 지적).
  • 항목 7: 판정 모델이 문제 목록을 객체로 써서 난 꼴 오류는 판정 요청 글의 답 꼴 줄이 목록 안의 꼴을 보이지 않아서였다. 답 꼴 줄을 고치고 190번을 모두 다시 돌렸다.
  • 항목 1: 기능 서브이슈마다 설계를 모두 정한 뒤 만들기 전에 Codex 설계 검토를 1차, 2차 받는다(사용자 지적).

검토에서 있었던 일

  • Codex 설계 검토 1차 지적 5(심각 2), 2차 4. 비교용 청크 수 맞추기, 다른 판 검색과 번역 고치기를 한 표로 정하기, 판정 순서, 꼴 검사, 처음 계획의 답을 써 두기가 여기서 들어갔다.
  • Codex 닫는 검토 1차 지적 5(보통 3, 낮음 2), 모두 반영했다. 충분성 판단 때 견줄 값을 같은 질문으로 다시 재게 한 것, 온도 시험의 원본 출력을 대화 기록에서 되살린 것, "짝 질문도 175라 오를 자리가 없다"는 말을 시험한 범위로 좁힌 것, 그림과 페이지에 남은 옛 흐름, "고치기 67번"의 조건이다.
  • 닫는 검토 2차는 1차 다섯 가운데 넷 해소, 그림 하나는 절반만 됨으로 보았다. 확대 페이지 전체 흐름 그림의 화살표를 지금 흐름(계획 쓰기에서 바로 첫 검색)으로 다시 그리고, 뺀 칸은 이어지지 않은 회색 점선 칸으로 남겼다.

계획과 달라진 것

  • 도구 호출 검색을 만들지 않았다. 이슈 체크리스트의 9번째 일(설계 검토)과 10번째 일(만들고 재기)은 하지 않았다.
  • 1단계 고리에서 저지먼트와 리파이먼트를 뺐다. 전체 그림에서 두 칸은 점선 "뺌"이다.
  • 190번을 네 번 시작했다. 꼴 오류의 원인(판정 요청 글의 답 꼴 줄, 계획 쓰기의 온도)을 고칠 때마다 모두 다시 돌렸다.

뒤 단계가 기대는 것

  • 첫 검색의 청크: 원래 질문 8개와 다른 판 위쪽 4개씩. 충분성 판단과 재검색, 정밀도 지표가 이 목록에서 시작한다.
  • 시간 기록의 두 길(send, timed). 새 기능의 모델 요청과 칸도 이 두 길을 지나가야 한다.
  • 미정 목록의 충분성 판단 줄: 도구 호출 검색의 완료 기준, 첫 검색은 1번이라도 줄면 원인을 찾는 기준, 툴 콜링과 JSON 가운데 무엇으로 할지, 도구 수와 호출마다 남길 칸.
  • 판정 모델(gemma3:4b)을 충분성 판단과 판정에 계속 쓸지는 그때 후보를 재서 정한다. 이번에 계획 판정을 바르게 한 것은 8개 가운데 2~3개였다.

남은 것

  • 1단계 저지먼트에 RAG를 붙여 청크를 보며 계획을 검사하는 안(사용자, 2026-10-27). 충분성 판단과 겹치는지 그 설계 때 본다. 이슈 #13에서는 "1단계 judgement에 RAG를 붙히는건 일단 아니라고" 정했었다.
  • 질문과 같은 언어의 판을 생성 모델 대신 코드가 원문으로 넣을지. 개발용 질문으로 다시 돌릴 때 본다.
  • 판정 빼기와 시간 기록이 한 커밋(be1b1b8)에 들어갔다. 실행 프로그램의 기본 경로가 이번 꼴의 기록 파일을 가리키는 것은 충분성 판단 때 고친다.

다시 볼 곳

툴유즈는 검색을 실행하는 칸이고, 무엇으로 찾을지는 2단계 생성이 고른다전체 그림에 칸마다 LLM과 코드를 표시해 설명함쓰이는 곳: 충분성 판단과 재검색 설계
