이슈 #14 · 6단계 시스템 만들기 · 2026-10-26

요청 분석과 1단계 고리 + 도구 호출 검색

지금 시스템이 근거를 못 찾는 질문을 줄이려고, 검색하기 전에 "무엇을, 어떤 검색어로 찾을지"를 먼저 정하게 만드는 일입니다. 이 페이지는 지금 상황, 바꾸려는 것, 질문 하나가 바뀐 시스템을 지나가는 길, 정할 것을 차례로 보여 줍니다.

진행하는 법

  1. "전체 흐름"부터 "질문 하나가 지나가는 길"까지 읽습니다.
    이해가 안 되는 곳이 있어도 넘어가셔도 됩니다. 채팅에서 하나씩 다시 봅니다.
  2. 정할 것은 채팅에서 하나씩 여쭙니다.
    물을 때는 "정할 것 1 · 검색어의 꼴"처럼 아래 "정할 것" 표의 번호와 이름을 함께 씁니다. 질문마다 왜 정해야 하는지, 안마다 무엇이 달라지는지, 추천을 붙입니다.
  3. 답하시면 이 페이지가 바뀝니다.
    "정할 것" 표의 상태가 "정함"이 되고, "질문 하나가 지나가는 길"의 그 자리에 정한 내용이 들어갑니다.
  4. 다 정하면 AI가 만들고 잽니다.
    결과는 "잰 결과" 표에 들어가고, 남길지 뺄지는 채팅에서 여쭙니다.
지금

정함 6개: 정할 것 1~6(검색어의 꼴, 요청 횟수, 검색 계획의 칸과 요청 글, 계획 검사의 기준과 요청 글, 고치기 한도와 요청 글, 청크 합치기). 지금 묻는 것: 정할 것 7 · 재는 법과 남길 기준.

전체 흐름: 질문 하나가 답이 되기까지

질문 하나가 거치는 열 칸입니다. 노란 칸을 이번 이슈에서 붙이고, 회색 칸은 지금 시스템에 이미 있으며, 점선 칸은 뒤 이슈에서 붙입니다. 빨간 점선은 떨어졌을 때 되돌아가는 길입니다.

칸마다 한 줄
  1. ①계획 쓰기 생성 모델이 찾을 것과 질문의 한국어판·영어판을 씁니다.이번 이슈
  2. ②계획 검사 판정 모델이 계획을 질문과 맞대어 봅니다. 문서는 보지 않습니다.이번 이슈
  3. ③계획 고치기 떨어지면 생성 모델이 고치고 다시 검사받습니다.이번 이슈
  4. ④첫 검색 원래 질문, 한국어판, 영어판으로 검색해 청크를 가져옵니다. 여기서 처음 검색합니다.이번 이슈
  5. ⑤충분성 판단 가져온 청크로 답할 수 있는지 봅니다.뒤 이슈: 충분성 판단과 재검색
  6. ⑥검색어 고치기·재검색 모자라면 생성 모델이 가져온 청크를 보고 검색어를 고쳐 다시 검색합니다. 최대 2번.뒤 이슈: 충분성 판단과 재검색
  7. ⑦답 쓰기 질문 원문과 청크로 답을 씁니다.지금 있음
  8. ⑧답 판정 답의 주장마다 청크에 근거가 있는지 봅니다.뒤 이슈: 판정과 신뢰도 점수
  9. ⑨답 고치기 떨어지면 답을 고치거나, 근거가 모자라면 재검색으로 돌아갑니다.뒤 이슈: 답 고치기
  10. ⑩내보내기 답, 참조 청크, 신뢰도를 내보냅니다.뒤 이슈: API
짚어 둘 것
  • 1단계 고리에서는 검색하지 않습니다. 청크 검색은 모두 2단계 고리에서 합니다.
  • 과제의 "부족 시 쿼리 재구성 후 재검색(최대 2회)"은 ⑥입니다. ③ 계획 고치기는 검색이 아니라서 이 2회에 들어가지 않습니다(decisions/stage4.md 2026-10-26).
  • 계획이 잘못돼도 지금 시스템보다 나빠지지 않습니다. ④에서 원래 질문 검색이 늘 들어가고, 뒤 이슈에서 ⑥이 붙으면 실제 청크를 보고 검색어를 다시 고칠 기회가 생깁니다.
  • 이번 이슈에서 잴 때는 ⑤⑥⑧⑨가 아직 없습니다. ④에서 가져온 청크가 그대로 ⑦ 답 쓰기로 갑니다.

지금 상황

지금 시스템이 하는 일

질문을 그대로 검색어로 씁니다. 한국어 청크와 영어 청크가 한곳에 들어 있는 데이터베이스에서, 언어를 가리지 않고 질문과 뜻이 가장 가까운 청크(문서를 잘라 놓은 조각) 8개를 가져옵니다. 그 8개를 질문과 함께 생성 모델에게 주고 답을 쓰게 합니다.

기대하는 것

영어 질문이라도 한국어판으로 한 번 더 검색하면, 한국어 문서에만 있는 근거에 닿을 수 있습니다. 지금 시스템이 놓친 영어 질문 5개 가운데 4개는, 사람이 미리 써 둔 한국어 짝 질문으로 검색했을 때 근거를 찾았습니다(1등 3개, 2등 1개). 모델이 쓴 한국어판으로도 그런지는 이번 이슈에서 잽니다.

두 번에 나눠 붙입니다

먼저, 검색 계획만 붙이고 검색은 코드가 계획의 검색어로 부릅니다. 그다음, 생성 모델이 검색 도구를 직접 부르게 바꿉니다(도구 호출 검색). 따로 재야 둘이 각각 얼마나 바꿨는지 보입니다.

질문 하나가 지나가는 길

지금 시스템이 놓친 영어 질문 q03-en 하나가, 바꾼 시스템의 칸을 차례로 지나갑니다. 정할 것 N · 이름은 아직 정하지 않은 자리입니다. 예는 AI가 쓴 것이고 아직 돌려서 나온 것이 아닙니다.

질문
질문 원문 (영어)

What is the mass in kg of a rectangular cuboid of yttrium that is 3 cm wide, 4 cm long, and 5 cm high? (Use its density near room temperature.)

한국어 뜻

가로 3 cm, 세로 4 cm, 높이 5 cm인 이트륨 직육면체의 질량은 몇 kg인가? (상온 근처의 밀도로 계산한다)

정답과 근거

정답 0.26832 kg. 계산에 필요한 이트륨의 밀도(4.472 g/cm³)는 한국어 문서 「이트륨」에만 있고, 영어 「Yttrium」 문서는 검색 대상에 없습니다.

지금 시스템에서는

영어 「Ytterbium」(이터븀, 이름이 비슷한 다른 원소) 문서와 「Isotopes of yttrium」(이트륨 동위 원소) 문서의 청크만 가져와, 5번 모두 "밀도가 주어지지 않아 답할 수 없다"고 답했습니다.

질문 글

하는 일

코드가 생성 모델에게 요청 글(지시문)과 질문을 보냅니다. 요청 글에는 "이 질문에서 찾을 것과 조건과 단위를 적고, 질문 전체를 한국어로 쓴 판과 영어로 쓴 판을 하나씩 써라"라고 적습니다. 번역기는 따로 두지 않습니다. 생성 모델이 한국어와 영어를 둘 다 하므로 스스로 옮깁니다. 질문이 어느 언어인지 가릴 필요가 없어, 한국어와 영어가 섞인 질문에서도 두 판이 늘 하나씩 생깁니다.

검색어가 되는 것

원래 질문, 한국어판, 영어판 세 개입니다. 원래 질문을 늘 그대로 검색하므로, 모델이 판을 잘못 써도 지금 시스템보다 나빠지지 않습니다. 찾을 것·조건·단위는 검색어로 쓰지 않고, 다음 칸(계획 검사)에서 두 판이 빠뜨린 것이 없는지 견주는 데 씁니다. 정함 · 정할 것 1 · 검색어의 꼴

넘기는 것

검색 계획

요청 횟수

모델에게 한 번 물어 검색 계획 전체(찾을 것, 조건, 단위, 한국어판, 영어판)를 한꺼번에 받습니다. 옮긴 판이 줄거나 바뀌는 문제가 되풀이되면 먼저 요청 글을 고치고, 그래도 안 되면 두 번으로 나눕니다. 정함 · 정할 것 2 · 요청 횟수

예 · 모델이 쓸 검색 계획
reason: 질량을 구하려면 부피(3×4×5 cm)와 밀도가 필요하다. 부피는 질문에 있으므로 문서에서 찾을 것은 이트륨의 밀도다. targets: [ fact: 이트륨의 밀도 · condition: 상온 근처 · unit: g/cm³ ] korean_question: 가로 3 cm, 세로 4 cm, 높이 5 cm인 이트륨 직육면체의 질량은 몇 kg인가? (상온 근처의 밀도로 계산한다) english_question: What is the mass in kg of a rectangular cuboid of yttrium … (원래 질문을 그대로 옮겨 씀)
요청 글 (영어) 정함 · 정할 것 3 · 검색 계획의 칸과 요청 글
You prepare a document search for the question. Do not answer the question. Answer only in the JSON format below. {"reason": "...", "targets": [{"fact": "...", "condition": "...", "unit": "..."}], "korean_question": "...", "english_question": "..."} reason: before the plan, write how you found the facts to look up and anything that was hard to translate. targets: every fact that must be looked up in documents to answer the question, one item per fact. Write them in the language of the question. fact: the fact to look up. condition: conditions attached to that fact, such as time, place, or state. Write "" if there are none. unit: the unit of that fact. Write "" if there is none. korean_question: the whole question written in Korean. If the question is already in Korean, copy it as it is. english_question: the whole question written in English. If the question is already in English, copy it as it is. For korean_question and english_question: write common words such as element names in that language. Keep numbers, symbols, abbreviations, units, and names of people and organizations as they are. Do not add, drop, shorten, or answer anything.
요청 글의 한국어 뜻
  1. 너는 이 질문으로 문서를 검색할 준비를 한다. 질문에 답하지 마라.
  2. 아래 JSON 꼴로만 답하라.
  3. (칸의 꼴: 생각 과정, 찾을 것 목록, 한국어판, 영어판)
  4. reason: 계획을 쓰기 전에, 찾을 사실을 어떻게 찾았는지와 옮기기 어려웠던 것을 써라.
  5. targets: 질문에 답하려면 문서에서 찾아야 하는 사실을 모두, 사실 하나에 항목 하나로. 질문의 언어로 써라.
  6. fact: 찾을 사실.
  7. condition: 그 사실에 붙은 조건(때, 곳, 상태 같은 것). 없으면 ""로 써라.
  8. unit: 그 사실의 단위. 없으면 ""로 써라.
  9. korean_question: 질문 전체를 한국어로 쓴 것. 질문이 이미 한국어면 그대로 옮겨 써라.
  10. english_question: 질문 전체를 영어로 쓴 것. 질문이 이미 영어면 그대로 옮겨 써라.
  11. 두 판 모두: 원소 이름 같은 일반 낱말은 그 언어로 써라. 숫자, 기호, 약어, 단위, 사람·기관 이름은 그대로 둬라. 더하거나, 빼거나, 줄이거나, 답하지 마라.

찾을 것이 여럿인 질문(예: 두 원소의 밀도를 견주는 질문)은 targets에 항목이 여럿 나옵니다. 분야 이름과 예시 질문은 일부러 넣지 않았습니다. 모델 설정은 지금 답 쓰기와 같습니다. reason(생각 과정)은 실행 기록에만 남겨, 계획이 틀렸을 때 왜 그렇게 썼는지 보고 요청 글을 고치는 데 씁니다. 판정 모델에게는 보여 주지 않습니다.

낱말뜻
지금 시스템 (최소판)질문을 그대로 검색어로 써서 한 번 검색하고, 가져온 청크 8개를 넣어 답을 쓰는 시스템. 여기에 기능을 하나씩 붙여 나갑니다.
청크문서를 잘라 놓은 조각. 검색하면 검색어와 뜻이 가까운 청크가 돌아옵니다.
근거를 찾음답 쓰기로 넘긴 청크 가운데 정답의 근거 줄이 든 청크가 하나라도 있는 것.
검색 계획검색하기 전에 생성 모델이 쓰는 것. 찾을 것 목록(항목마다 사실, 조건, 단위), 질문의 한국어판, 영어판.
요청 글코드가 모델에게 질문과 함께 보내는 지시문. 모델이 무엇을 어떤 꼴로 답할지 적습니다.
생성 모델검색 계획과 답을 쓰고 검색 도구를 부르는 모델, qwen3:8b.
판정 모델생성 모델이 쓴 것을 검사하는 모델, gemma3:4b.
임베딩 모델 (bge-m3)글을 숫자 목록(벡터)으로 바꾸는 모델. 뜻이 가까운 글은 가까운 숫자 목록이 됩니다. 검색은 이 가까움으로 청크를 고릅니다.
1단계 고리문서와 검색 없이 생성 → 저지먼트 → 리파이먼트를 되풀이해 검색 계획을 다듬는 부분.
2단계 고리검색 도구로 청크를 가져와 답을 쓰고 검사하는 부분. 이번에는 앞의 생성·툴유즈만 붙입니다.
저지먼트 / 리파이먼트참고 PDF의 칸 이름. 저지먼트는 앞 칸이 만든 것을 검사해 통과·불통과를 정하고, 리파이먼트는 그 지적을 받아 고칩니다.
툴유즈 / 관찰값참고 PDF의 칸 이름. 툴유즈는 모델이 도구(여기서는 검색 도구)를 부르는 칸, 관찰값은 도구가 돌려준 결과(여기서는 청크)입니다.
도구 호출 검색코드가 정해진 대로 검색하는 대신, 생성 모델이 어떤 검색어로 검색할지 정해 검색 도구를 부르는 방식.
LangGraph모델 요청과 도구 실행을 칸과 화살표로 이어 흐름을 만드는 파이썬 라이브러리.
ReAct모델이 생각하고, 도구를 부르고, 결과를 보고 다시 생각하기를 되풀이하는 방식.
