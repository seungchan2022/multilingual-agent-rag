# PostgreSQL과 pgvector 설명

5단계에서 조합 8개의 청크와 벡터를 넣고 검색할 저장소를 설명한다. 4단계에서 "설치하기 전에 AI가 설명 문서를 만들고 사용자가 읽고 묻는다"고 정했다(`decisions/stage4.md` 2026-10-23 "벡터 스토어는 PostgreSQL + pgvector로 한다" 줄 ㉢). 마지막 절에 사용자가 고를 것(설치 방법)이 있다.

## 1. PostgreSQL

**정의.** PostgreSQL은 데이터를 표(테이블)에 저장하고, SQL이라는 질의 언어로 꺼내 주는 데이터베이스 서버다. 표는 줄(행)과 칸(열)으로 되어 있고, 칸마다 무엇이 들어가는지(글자, 정수 등)가 정해져 있다.

**특징.**
- 프로그램과 따로 도는 서버다. 서버를 켜 두면 Python 프로그램이 연결해서 줄을 넣고 꺼낸다. 이번에 넣은 `psycopg`가 Python에서 연결하는 패키지다.
- 데이터는 파일로 디스크에 남는다. 프로그램을 끄고 다시 켜도 넣은 줄이 그대로 있다.
- 실제 서비스와 회사에서 널리 쓴다. 4단계에서 이것을 고른 까닭이 이것이다(결정 줄 ㉣ "실제 서비스와 회사에서 쓰는 DB에 벡터 검색을 붙여 보며 공부한다").

**이 과제에서.** 청크 하나가 표의 한 줄이다. 칸은 4단계에서 글, 벡터, 문서 이름, 원문 줄 범위, 언어로 정했다(결정 줄 ㉡). 칸의 세부(이름, 조합 8개를 표 8개로 둘지 한 표에 조합 칸을 둘지)는 구현하면서 정해 알린다.

## 2. pgvector

**정의.** pgvector는 PostgreSQL에 붙이는 확장이다. 확장은 PostgreSQL에 없던 기능을 더하는 추가 부품이다. pgvector가 더하는 것은 둘이다.
- `vector`라는 칸의 종류: 숫자 여러 개(예: bge-m3는 1,024개, gte는 768개)를 한 칸에 넣는다.
- 두 벡터 사이의 거리를 재는 연산자: `<=>`(코사인 거리), `<->`(직선 거리), `<#>`(내적의 음수).

**특징.**
- 확장 파일은 PostgreSQL의 판(16, 17, 18)마다 따로 만들어진다. 16용 파일은 18에 붙지 않고, 18용 파일은 16에 붙지 않는다. 아래 4절의 문제가 여기서 생긴다.
- 확장을 설치한 뒤에도 쓰려는 데이터베이스마다 `CREATE EXTENSION vector;`를 한 번 실행해야 켜진다.

**코사인 거리.** 두 벡터가 가리키는 방향이 얼마나 다른지다. 코사인 거리 = 1 − 코사인 유사도이고, 0에 가까울수록 뜻이 가깝다. 4단계에서 벡터를 길이 1로 맞춰(L2 정규화) 넣고 코사인 거리가 작은 순서로 순위를 매기기로 정했다(`decisions/stage4.md` "Codex 1차 검토" 줄 ㉥). 설치 확인 때 같은 뜻의 한국어·영어 문장 둘의 코사인 유사도가 bge-m3 0.916, gte 0.840이었다. 코사인 거리로는 0.084와 0.160이다.

## 3. 검색은 이렇게 한다: 정확한 검색과 근사 검색

**정확한 검색.** 질문 벡터와 표의 모든 청크 벡터의 거리를 하나씩 재고, 가까운 순서로 k개를 꺼낸다.

```sql
-- 정확한 검색: 인덱스 없이 모든 줄과 거리를 잰다
SELECT chunk_id, embedding <=> :질문벡터 AS 거리
FROM chunks
ORDER BY 거리, chunk_id
LIMIT 4;
```

**근사 검색.** 벡터 인덱스(HNSW, IVFFlat)를 먼저 만들어 두고, 모든 줄을 재지 않고 가까울 것 같은 곳만 잰다. 빠르지만 가장 가까운 청크를 가끔 놓친다.

```sql
-- 근사 검색: 인덱스를 만들면 같은 질의가 인덱스를 거쳐 빨라지지만 결과가 조금 다를 수 있다
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
SELECT chunk_id, embedding <=> :질문벡터 AS 거리
FROM chunks
ORDER BY 거리
LIMIT 4;
```

**이 과제에서.** 정확한 검색만 쓴다. 인덱스를 만들지 않는다(결정 줄 ㉠). 조합 사이의 차이가 검색 방식이 아니라 모델과 청크에서만 오게 하기 위해서다. 청크가 수천 개 규모라 모두 재도 느리지 않다. 거리가 같으면 청크 ID 순서로 매긴다(`decisions/stage4.md` "MiniLM은 비교에서 재기 전에 뺀다" 줄). 위 첫 질의의 `ORDER BY 거리, chunk_id`가 그 규칙이다.

## 4. 고를 것: pgvector를 붙이는 방법

**왜 정해야 하는가.** 이 컴퓨터에는 PostgreSQL 16(Homebrew)이 있다. 그런데 Homebrew가 내려 주는 pgvector(0.8.7)는 PostgreSQL 17과 18용으로만 만들어진다(Homebrew의 pgvector 설치 규칙 파일에서 2026-10-23 확인). 그래서 16에는 바로 붙지 않고, 아래 셋 가운데 하나를 골라야 한다.

지금 상태(2026-10-23 확인):
- PostgreSQL 16 서버는 꺼져 있다. 데이터 폴더(`/opt/homebrew/var/postgresql@16`)는 39MB다. 이 안에 다른 프로젝트의 데이터베이스가 있는지는 서버를 켜 보지 않아 확인하지 않았다.
- Docker는 설치되어 있으나 꺼져 있다.
- 디스크는 14GB가 남아 있다.

| 안 | 하는 일 | 이 안이면 달라지는 것 |
|---|---|---|
| **A. PostgreSQL 18로 올린다 (추천)** | `brew install postgresql@18 pgvector`로 18과 18용 pgvector를 받는다. 16은 지우지 않고 그대로 둔다 | 명령 두 줄로 끝나고, 나중에 pgvector를 올릴 때도 `brew upgrade`면 된다. 16과 18이 같은 연결 번호(포트 5432)를 쓰므로 둘을 함께 켜지 않는다(16은 지금 꺼져 있다). 18은 2025-09에 나온 판이라 16보다 지원 기간이 길다 |
| B. 16에 pgvector를 직접 만들어 붙인다 | pgvector 소스를 받아 16의 설정(`pg_config`)으로 컴파일해 16 폴더에 넣는다 | 16을 그대로 쓴다. 대신 Homebrew가 관리하지 않는 파일이 16 폴더에 생기고, 16이나 pgvector를 올릴 때마다 다시 컴파일해야 한다. "명령으로 다시 만들 수 있다"(5단계 완료 기준)를 지키려면 이 컴파일 명령도 기록에 남겨야 한다 |
| C. Docker로 pgvector가 들어 있는 PostgreSQL을 띄운다 | pgvector 쪽이 내는 Docker 이미지(PostgreSQL 판마다 따로 있다)로 서버를 띄운다 | 이 컴퓨터의 PostgreSQL을 건드리지 않는다. 대신 쓸 때마다 Docker를 켜야 하고, 이미지와 데이터가 디스크를 더 쓴다. 회사에서 흔히 쓰는 방식에 가깝다 |

**추천은 A다.** 4단계에서 정한 것(실제 서비스에서 쓰는 DB에 벡터 검색을 붙여 공부)은 판과 상관없이 같다. 16을 고집할 까닭은 기록에 없다(4단계 결정의 16은 "이 컴퓨터에 있는 것"을 적은 것이다). 셋 가운데 손이 가장 적게 가고 다시 만들기도 가장 쉽다. 17이 아니라 18인 까닭은 지원 기간이 더 길다는 것 하나다. 이 과제에서 17과 18의 차이가 결과에 드러나는 곳은 없다.

**어느 안이든 검색 결과는 같다.** 정확한 검색은 저장소나 판이 달라도 같은 청크를 같은 순서로 내놓는다(결정 줄 ㉠). 고르는 것은 설치와 관리의 수고이고, 실험의 결론은 바뀌지 않는다.
