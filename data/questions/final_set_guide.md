# 질문 후보를 만드는 순서표 (사용자용)

이 글 하나만 보고 처음부터 끝까지 따라 한다. 개발용 질문과 최종 평가용 질문을 같은 순서로 만든다. 둘이 다른 곳은 단계 안에 **개발용:**, **최종:**으로 나눠 적었다.

- 최종 평가용 질문은 Claude(Opus), 서브에이전트, Codex가 7단계 전에 보면 안 된다. 그래서 최종 평가용은 사용자가 이 글을 보고 혼자 한다. 개발용은 같은 순서를 먼저 해 보며 이 글과 지시서의 빈 곳을 찾는 자리다(`decisions/common.md` 2026-10-15).
- 쓰는 AI: 후보는 Gemini 앱(Google AI Pro, 모델 3.1 Pro, 사고 수준 최고, 임시 채팅), 영어가 낀 질문의 유형 확인은 ChatGPT(Plus, GPT-6, 추론 수준 High, 임시 채팅)다(`decisions/stage3.md` 2026-10-15).
- 붙여 넣는 글은 두 가지다. 긴 본문은 `data/questions/final_set_instructions.md`(이하 "지시서") 파일 전체다. 짧은 메시지는 이 글의 상자 안에 있다. 상자는 안쪽 줄만 복사한다(맨 위와 맨 아래의 백틱 줄은 빼고).
- 명령은 VS Code의 터미널이나 Claude Code 대화창(맨 앞에 `! `를 붙여)에서 프로젝트 폴더를 기준으로 돌린다.
- 파일을 저장할 때는 저장 창에서 폴더를 눌러 고르고, 이름 칸에는 파일 이름만 적는다. 이름 칸에 경로를 적으면 폴더가 새로 생긴다.

**저장할 곳**
- **개발용:** 지금 채팅은 `research_notes/stage3_dev/chat4` 폴더다(Claude가 만들어 둠). 묶음 1은 앞 채팅(`chat3`)에서 받아 대조를 마쳤으므로, 묶음 2~5 명령의 `--previous`에서 묶음 1 파일만 `chat3`을 가리킨다. 새 채팅에 붙일 앞 묶음의 질문 문장은 `chat4/previous_questions.md`에 있다. 아래 단계의 폴더와 명령은 모두 이 폴더로 적었다. 개발용에서 새 채팅을 열 때는 Claude가 폴더를 새로 만들고 이 글의 `chat3`을 다음 번호로 바꿔 둔다.
- **최종:** `<3단계에서 정한다>`(프로젝트 폴더 밖). 정해지면 아래 "최종:" 명령의 폴더 자리를 채운다.

## 3. 마지막 파일과 읽기 시험 (메시지 3)

Gemini가 28개를 모두 실제로 가지고 있는지 확인하는 단계다. 문서마다 정해 준 줄을 글자 그대로 옮기게 하고, 프로그램이 원문과 대조한다. 가지고 있지 않은 문서는 글자 그대로 옮길 수 없다(`decisions/stage3.md` 2026-10-15 "읽기 시험").

1. **메시지 3**: 21번째 `wiki-ko-cheonan.md`부터 맨 끝 `wiki-ko-suwon.md`까지(`wiki-ko-` 8개) 올리고, 아래 글 전체를 붙여 보낸다. 안의 ```` ```yaml ```` 부분까지 넣는다.

````text
이번이 세 번째이고 파일은 8개다. 이제 28개를 다 올렸다. 아직 질문 후보는 만들지 마라.

먼저 네가 올린 문서를 실제로 다 읽을 수 있는지 확인한다. 기억이나 짐작으로 쓰지 말고 문서에서 글자 그대로 옮겨라. 대상은 이번 메시지의 파일 8개만이 아니다. 첫 번째, 두 번째, 세 번째 메시지로 올린 문서 28개 전부다. 28개 각각에 대해 아래를 적는다. `doc_id`는 파일 이름에서 `.md`를 뺀 것이다.

- 줄이 `## `(샵 두 개와 빈칸)로 시작하는 줄을 이 글에서 "큰 제목"이라 부른다. `### `로 시작하는 줄은 큰 제목이 아니다.
- 큰 제목이 있는 문서: 큰 제목마다 문서에 나온 순서대로, 그 줄 전체를 글자 그대로(`## ` 포함) `heading`에 적고, 그 아래에서 처음 나오는 빈 줄이 아닌 줄의 앞부분을 `next_line`에 적는다. 그 줄이 표의 줄이든 목록이든 작은 제목이든 그대로 옮긴다.
- 큰 제목이 없는 문서: 맨 첫 줄(`# `로 시작하는 줄) 다음에 처음 나오는 빈 줄이 아닌 줄의 앞부분을 `first_line`에, 문서의 맨 마지막 빈 줄이 아닌 줄의 앞부분을 `last_line`에 적는다.
- "앞부분"은 그 줄의 맨 처음부터 30글자 이상을 글자 그대로 옮긴 것이다. 줄이 30글자보다 짧으면 줄 전체를 옮긴다. 중간을 건너뛰거나 바꾸지 마라.
- 받지 못했거나 읽을 수 없는 문서가 있으면 그 문서에 `status: 읽지 못함`을 적는다. 숨기지 마라.
- 모든 글자 값은 큰따옴표로 감싼다. 값 안의 큰따옴표는 `\"`로 적는다.

YAML 코드 블록 하나에 28개를 모두 넣어 낸다. 모양은 아래와 같다(값은 지어낸 것이다).

```yaml
- doc_id: wiki-en-example
  sections:
    - heading: "## History"
      next_line: "The town was first recorded in the 12th"
    - heading: "## Sister cities"
      next_line: "| City | Country | Year |"
- doc_id: kto-ko-example
  first_line: "예시 마을은 강을 따라 길게 늘어선 작은"
  last_line: "가을에는 강변을 따라 축제가 열린다."
- doc_id: wiki-ko-missing
  status: 읽지 못함
```
````

2. 답이 끝까지 나온 뒤(답 아래에 복사 단추들이 보인 뒤) 답의 YAML 상자에서 복사 단추를 누르고, VS Code 새 파일(`Cmd+N`)에 붙여 넣은 뒤 `Cmd+S`로 저장한다.
   - 저장 창의 폴더: `research_notes` → `stage3_dev` → `chat4`
   - 이름 칸: `read_test_batch2.yaml`처럼 이번에 받을 묶음의 번호를 붙인다
   - 이 답은 원문의 글자뿐이라 **최종**에서도 같은 자리(새 `chat` 번호 폴더)에 저장해도 된다.
3. 검사를 돌린다.

```

```

4. 마지막 줄이 `문서 28개 가운데 28개 통과`로 시작하면 4단계로 간다(뒤에 `(그 가운데 N개는 줄 중간부터 옮김)`이 붙어도 된다). 아니면 후보를 요청하지 않고 "문제가 생겼을 때"를 본다.

## 후보 YAML 칸의 뜻

Gemini가 낸 후보 하나는 아래 칸으로 이뤄진다. 대조 카드(6단계)는 이 칸들을 읽기 좋게 옮겨 놓은 것이다. 카드, 판정 칸의 "볼 곳", 이 글은 모두 칸을 `영어 칸 이름`(한국어 뜻)으로 같이 적는다.

| 칸 | 뜻 |
|---|---|
| `id`(후보 번호) | 후보 번호. 묶음 1은 `c-001`~`c-012`, 묶음 2는 `c-013`부터 |
| `question`(질문) | 질문 문장 |
| `question_language`(질문 언어) | 질문을 쓴 언어(`ko` 한국어, `en` 영어) |
| `evidence_language`(근거 언어) | 근거가 있는 문서의 언어. 답 없는 질문은 `null` |
| `type`(유형) | 유형. `single_fact` 단일 사실, `table_numeric` 표·수치·조건, `multi_doc` 여러 문서 연결, `paraphrase` 표현 불일치, `no_answer` 답 없음 |
| `answer`(정답) | 정답 문장. 답 없는 질문은 `null` |
| `required_facts`(꼭 필요한 사실) | 정답에 꼭 들어가야 하는 사실들. 여러 개면 모두 있어야 정답이다 |
| `fact`(사실) | 그 사실 하나를 적은 문장 |
| `evidence`(근거) | 그 사실의 근거 목록. 비어 있으면(`[]`) 다른 사실들에서 나오는 결론이다(예: "A가 B보다 많다") |
| `doc_id`(문서) | 근거를 가져온 문서의 이름. 파일 `data/corpus/markdown/<doc_id>.md`다 |
| `location`(위치) | 그 구절이 있는 절의 제목 |
| `passage`(근거 구절) | 근거 구절. 원문에서 글자 그대로 옮긴 것이다. 표면 머리글 행과 해당 행 |
| `opposite_check`(반대 언어 찾을 말) | Gemini가 고른, 반대 언어 문서 14개에서 찾을 말의 목록(예: `1969`, `Chuncheon`). 이 말이 나오는 곳(걸린 곳)은 프로그램이 찾아 카드에 넣는다. 글자가 같으면 뜻과 상관없이 다 걸린다 |
| `same_language_check`(같은 언어 찾을 말) | Gemini가 고른, 같은 언어 문서 14개(근거 문서 포함)에서 찾을 말의 목록. 걸린 곳은 프로그램이 찾고, 이 후보의 근거 구절 안은 빼고 보인다 |
| `expected_refusal`(기대하는 거절) | (답 없는 질문) 맞는 대답이 무엇인지. 예: "그런 것은 없다고 답한다" |
| `no_answer_reason`(답이 없다고 본 까닭) | (답 없는 질문) 어디를 찾아봤고 왜 답이 없는지, 왜 일반 지식으로도 답할 수 없는지 |
| `rebuttal`(반박 구절) | (답 없는 질문) 전제를 반박하는 원문 구절. 없으면 `[]` |

걸린 곳으로 확인하는 까닭: 반대 언어 문서에 같은 사실이 있다면 그 문장에는 그 사실의 숫자나 이름이 들어 있을 가능성이 크다. 그래서 숫자와 이름이 나오는 곳을 빠짐없이 모아 사람이 읽으면 같은 사실이 있는지 알 수 있다. 다른 말로 돌려 적은 곳은 이것으로 잡지 못하므로, 판정 칸 6(다른 말로 더 찾기)과 7(같은 도시 문서 통째로 읽기)을 함께 한다.

|---|---|---|
| 마지막 줄 `문서 28개 가운데 28개 통과` | Gemini가 28개를 모두 가지고 있다 | 4단계로 간다 |
| `통과(줄 중간부터 옮김)` | 긴 줄의 맨 처음이 아니라 중간부터 옮겼다. 그 글이 기대한 줄 안에 글자 그대로 한 번 있고 그 문서의 다른 값은 모두 맞다는 것을 프로그램이 확인했다. 문서를 가지고 있다는 뜻이다 | 통과로 센다. 따로 할 일은 없다 |
| `답에 이 문서가 없음` | 답에 그 문서가 빠졌다 | 후보를 요청하지 않는다. "문제가 생겼을 때"의 "읽기 시험 답에 이번 메시지의 파일만 있다" 또는 "파일 이름이 10개가 아니다"를 본다 |
| `줄의 앞부분이 아님` | 기대한 줄이 아닌 다른 줄을 적었거나, 글자를 바꿨다 | 후보를 요청하지 않는다. "문제가 생겼을 때"의 "읽기 시험 검사에서 실패한 문서가 있다"를 따른다 |
| `큰 제목 수가 다름`, `heading이 다름` | 문서를 정확히 옮기지 못했다 | 후보를 요청하지 않는다. 새 채팅에서 1단계부터 다시 한다 |
| `읽지 못함이라고 답함` | Gemini가 그 문서를 읽지 못했다고 했다 | 새 채팅에서 1단계부터 다시 한다 |
| `YAML을 읽지 못함 (N줄 M칸)`이고 N이 파일의 마지막 줄 근처 | 답이 덜 복사됐다 | 답이 끝까지 나온 뒤 다시 복사해 저장한다 |
| `답 파일이 없음` | 명령의 파일 경로나 이름이 저장한 것과 다르다 | 저장한 폴더와 이름을 확인한다 |

**후보 검사**(`check_candidates.py`)

| 출력 | 뜻 | 할 일 |
|---|---|---|
| 마지막 줄 `후보 12개 가운데 12개 통과, 묶음 구성 통과` | 형식과 찾기 기록이 맞다. 내용이 맞는지는 아직 모른다 | 6단계(대조)로 간다 |

| `찾을 말이 N곳에 나옴 (10곳까지 받는다)` | 너무 흔한 말이라 그 사실을 가려내지 못한다 | 고치게 한다 |
| `찾을 말만 글자로 적는다` | 찾을 말 대신 걸린 곳까지 적었다(예전 모양) | 고치게 한다 |

| `찾을 말이 반대 언어가 아님`, `찾을 말이 근거 문서의 언어가 아님`, `찾을 말이 N개임` | 찾을 말의 언어나 개수가 틀렸다 | 고치게 한다 |
| `id: 앞 묶음에서 이미 쓴 id`, `question: …의 질문과 글자 그대로 같음` | 앞 묶음과 겹친다 | 고치게 한다 |
| `근거 구절이 순서표 끝 "알려진 부딪히는 값"의 항목과 겹친다(자리 / 값 … / 해 …)` | 근거가 이 글 끝 목록의 사실(문서 안에서나 두 언어 문서 사이에서 값이 서로 다른 사실)이거나 그 값이 든 구절이다. "자리"는 목록의 원문 문장과 같은 자리, "값"은 목록의 값(두 자리 이상)이 구절에 있음, "해"는 값이 둘인 인구 표의 해의 줄이다. 넓게 잡으므로 관계없는 구절도 걸릴 수 있다 | 고치게 한다. 관계없어 보여도 그 자리에서 남기지 않는다(`decisions/stage3.md` 2026-10-16) |
| `실패  묶음 구성` 아래 `후보가 N개임`, `type …가 N개임`, `도시 갈래: …`, `표 구절을 가진 것이 없음` | 묶음의 개수나 구성이 틀렸다 | 모자란 칸을 "한 칸만 다시 요청할 때"로 요청한다 |
| `주의  <id>: …와 같은 문서·구절을 씀` | 다른 후보와 같은 근거를 썼다. 실패는 아니다 | 대조할 때 두 후보가 같은 사실을 묻는지 본다. 같으면 하나를 버린다 |
| 후보 아래 `찾은 기록: 찾을 말 N개, 걸린 곳 M곳` | 정보 줄이다. M은 프로그램이 반대 언어 문서에서 찾은 걸린 곳의 수 | 대조할 때 걸린 곳 M곳을 번역기로 읽는다 |
| 후보 아래 `같은 언어 찾은 기록: 찾을 말 N개, 걸린 곳 M곳` | 정보 줄이다. M은 프로그램이 같은 언어 문서(근거 문서 포함, 근거 구절 안은 뺌)에서 찾은 걸린 곳의 수 | 대조할 때 걸린 곳 M곳을 읽는다. 영어이면 번역기로 읽는다 |
| `YAML을 읽지 못함` | 덜 복사됐거나 Gemini가 YAML 모양을 틀렸다 | 줄이 파일 끝이면 다시 복사한다. 아니면 "실패한 후보를 고치게 할 때"를 따른다 |

## 대조할 것

후보 검사(5단계)가 이미 본 것은 다시 보지 않는다: 근거 구절과 반박 구절이 원문에 글자 그대로 있는지, 쓰면 안 되는 영어 소개 글 두 개(`kto-en-jeonju-hanok-village`, `kto-en-cheonan-samgeori-park`)를 썼는지, 표 구절에 머리글 행이 있는지, `opposite_check`(반대 언어 찾기 기록)가 원문과 맞는지, 근거 구절이 이 글 끝의 "알려진 부딪히는 값" 목록과 겹치는지.

후보마다 아래를 본다. 하나라도 걸리면 고치거나 버린다. 여분이 있으므로 애매하면 버린다.

답 있는 질문:

- `passage`(근거 구절)만 읽고 정답이 나오는가. 조건과 단위까지 들어 있는가.
- 질문이 깔고 있는 전제(개수, 날짜, 소속 등)가 문서와 맞는가. 예: 질문이 "5개 자치구 중"이면 근거 문서에 자치구가 5개인지 본다(`decisions/stage3.md` 2026-10-16).
- 정답이 하나로 정해지는가.
- 같은 것이 다른 값으로 적힌 곳이 없는가. ① 이 글 끝의 "알려진 부딪히는 값" 목록과 겹치는지는 후보 검사가 본다(넓게 잡는다. `decisions/stage3.md` 2026-10-16). 검사는 목록과 글자나 값이 겹칠 때만 잡으므로 아래 ②③은 그대로 한다. ② 근거 문서에서 그 대상을 가리키는 낱말(예: "면적", "인구", 자매도시 이름)을 `Cmd+F`로 찾아, 맨 위의 요약 목록, 본문, 표에 다른 값이 있는지 본다. 반올림하거나 버리거나 "약"을 붙여 적은 값(예: 1,090.9와 1,091)과 한쪽을 덜 자세하게 적은 값(예: "1986년 11월"과 "1986년")도 다른 값이다. 기준 날짜가 다르게 적혀 구분되는 값이 아니면 버린다. 값이 같고 적는 방식만 다른 것과, 같은 칸 괄호 안의 다른 단위 값은 다른 값이 아니다. 표의 합계·소계 값이면 그 아래 줄들을 더해 본다. ③ 같은 낱말로 VS Code의 폴더 찾기(`Cmd+Shift+F`, "포함할 파일"에 `data/corpus/markdown`)를 해서 같은 언어의 다른 문서에 다른 값이 있는지도 본다. 판정은 ②와 같다(예: `wiki-ko-suwon`의 장안구 인구 307,151명은 날짜가 없고 `portal-ko-suwon-population`의 동들을 더하면 2021-05-31 기준 277,206명이라 버린다). ④ 카드 3·4번에 프로그램이 `same_language_check`(같은 언어 찾을 말)로 찾은 걸린 곳마다 그 문장을 읽어, 같은 것이 다른 값으로 적혀 있지 않은지 본다. 영어이면 번역기에 붙여 읽는다. Gemini의 찾을 말은 ②③에 더하는 것이고 ②③을 대신하지 않는다. ⑤ 근거가 영어 문서이면 ②③의 낱말을 이렇게 얻는다: 위키백과 근거 문서는 카드에 적힌 원문 주소를 크롬에서 열어 "한국어로 번역"한 뒤 한국어 낱말과 숫자로 `Cmd+F` 하고(관광 소개 글은 짧으므로 통째로 번역기에 붙인다), 다른 문서의 폴더 찾기에는 그 대상의 한국어 낱말을 번역기로 영어로 옮긴 말과 숫자를 쓴다. 걸린 줄은 번역기에 붙여 읽는다(`decisions/stage3.md` 2026-10-16).
- `required_facts`(꼭 필요한 사실)가 정답에 꼭 필요한 사실을 빠짐없이, 군더더기 없이 담는가.
- 유형이 맞는가. 두 유형의 뜻에 다 맞으면 지시서 3번의 순서(`multi_doc`, `table_numeric`, 그다음 `single_fact` 또는 `paraphrase`)대로 먼저 맞는 유형으로 적혀 있는가. `table_numeric`은 답이 표에 있거나 여러 값 가운데 조건에 맞는 것을 골라야 하는 질문이다. 문장에 수치가 하나만 있으면 `table_numeric`이 아니다.
- `single_fact`와 `paraphrase`가 맞게 갈렸는가. 질문을 문서의 언어로 옮겼을 때 근거 구절의 핵심 낱말을 그대로 썼으면 `single_fact`, 다른 말로 바꿨으면 `paraphrase`다. 이름은 판단에서 뺀다. 가르기 어려우면 버린다. `paraphrase` 카드는 칸 9의 짝 목록(한 줄에 `질문 조각 → 근거 구절의 짝 (같은 말 / 바꾼 말 / 이름)`)을 먼저 채우고, 그다음 접힌 칸의 Gemini 짝과 견준다. 질문에 그대로 쓴 낱말("같은 말" 줄)이 답을 드러내면(예: 묶음 1 c-011의 "특별자치시") 바꾼 말을 찾지 않아도 답이 나오므로 버린다. "이름" 줄은 답을 가리키는 설명이라 이 판단에서 뺀다(`decisions/stage3.md` 2026-10-16). 질문이나 근거 구절이 영어이면 칸 9의 접힌 칸에 있는 ChatGPT의 짝 목록(6단계 0)을 보고 판단한다. 영어 말에는 한국어 뜻이 붙어 있다.
- 반대 언어 문서에 같은 사실이 없는가. ① 카드 5번에 프로그램이 `opposite_check`(반대 언어 찾을 말)로 찾은 걸린 곳마다 그 문장을 번역기에 붙여, 정말 같은 사실이 아닌지 본다. ② 찾을 말에 그 사실의 이름과 숫자가 들어 있는지 본다. 빠졌으면 그 말을 반대 언어로 옮겨(번역기) 폴더 찾기를 더 한다. ③ 근거가 두 언어 도시의 문서이면, 같은 도시의 반대 언어 문서를 통째로 번역해 그 사실이 있는지 본다. 위키백과 문서는 카드에 적힌 원문 주소(우리가 가져온 바로 그 판)를 크롬에서 열고, 오른쪽 클릭 → "한국어로 번역"으로 페이지 전체를 번역한 뒤 `Cmd+F`로 그 사실의 한국어 낱말과 숫자를 찾아 앞뒤를 읽는다. 절 이름으로 짐작해 골라 읽지 않는다(영어 문서의 절 이름은 한국어 문서와 다르다. 예: 춘천 한국어 "경제", 영어 "Industry"). 관광 소개 글은 짧으므로 파일 내용을 그대로 번역기에 붙인다. 반대 언어 문서가 한국어이면 직접 읽는다. 도시마다 한 번 번역해 둔 탭은 그 도시의 다른 후보에도 쓴다.

답 없는 질문:

- 문서 전체에서 한국어 표현과 영어 표현으로 찾아봐도 답이 없는가.
- 문서를 보지 않고 일반 지식으로도 답할 수 없는가. 세상에 실제로 답이 있는 질문이면 버린다.
- 전제가 너무 뻔하게 틀리지 않았는가.

## 문제가 생겼을 때

| 문제 | 할 일 |
|---|---|
| 파일을 올렸는데 답에 적힌 파일 이름이 10개(세 번째는 8개)가 아니다 | 빠진 파일을 같은 채팅에 다시 올린다. 그래도 빠지면 새 임시 채팅에서 1단계부터 다시 한다 |
| 읽기 시험 검사에서 실패한 문서가 있다 | 후보를 요청하지 않는다. 지금 채팅을 닫고 새 임시 채팅에서 1단계부터 다시 한다. 줄 중간부터 옮긴 경우(진행해도 되는 경우)는 프로그램이 이미 `통과(줄 중간부터 옮김)`으로 셌으므로, `실패`로 나온 것은 모두 다시 할 경우다(`decisions/stage3.md` 2026-10-16). 검사 출력은 원문의 글자뿐이라 Claude에게 보여도 된다 |
| 검사가 `YAML을 읽지 못함`을 내고, 그 줄이 파일의 맨 끝이다 | 답이 덜 복사된 것이다. 저장한 파일의 끝이 Gemini 화면의 답 끝과 같은지 보고, 답이 끝까지 나온 뒤 다시 복사해 저장한다(2026-10-15 chat3 읽기 시험에서 있었던 일) |
| 읽기 시험 답에 이번 메시지의 파일만 있다 | 새 임시 채팅에서 1단계부터 다시 한다. 2026-10-15에 지시서를 고쳐 생기지 않게 했다 |
| 후보 검사에서 실패한 후보가 있다 | 아래 "후보 검사에서 실패한 후보를 고치게 할 때"를 따른다. 두 번 고치게 해도 같은 후보가 실패하면 그 후보는 버리고 "한 칸만 다시 요청할 때"를 쓴다 |
| 묶음 구성(개수, 유형별 수, 도시 갈래)이 틀렸다 | 모자란 칸을 "한 칸만 다시 요청할 때"로 요청한다. 남는 후보는 버린다 |
| AI가 개수를 못 채웠다고 한다 | 모자란 칸과 이유를 적어 둔다. "한 칸만 다시 요청할 때"로 한 번 더 요청한다. 그래도 안 되면 그 칸은 코퍼스에 재료가 모자란 것이므로 멈추고 Claude에게 칸과 모자란 수만 알린다 |
| 반대 언어 문서에도 같은 사실이 있다 | 그 후보를 버린다 |
| 답 없는 질문인데 세상에는 답이 있다 | 그 후보를 버린다 |
| 유형이 애매하거나 정답이 여러 개로 읽힌다 | 고쳐 쓰지 않고 버린다 |
| 한 칸의 후보가 전부 버려졌다 | "한 칸만 다시 요청할 때"를 쓴다 |
| 임시 채팅이 끊겼다 | 새 임시 채팅에서 1단계부터 다시 한다. 4단계 첫 요청에 받아 둔 후보의 질문 문장을 "아래 질문들은 이미 쓰고 있다" 글로 붙인다 |

**후보 검사에서 실패한 후보를 고치게 할 때**

1. 그 묶음의 검사 명령(5단계)을 다시 돌리고, 출력 전체를 복사한다.
2. 같은 Gemini 채팅의 입력창에 아래 상자의 글을 붙이고, 한 줄 띄운 뒤 복사한 출력을 붙여 보낸다.
3. 답이 끝까지 나온 뒤, YAML 상자를 복사해 같은 폴더에 `batch<번호>_<묶음>_fix1.yaml`로 저장한다(예: `batch1_ko-ko_fix1.yaml`). 답 전체도 복사해 `batch<번호>_<묶음>_full_fix1.md`로 저장한다(고친 답의 YAML 뒤 메모를 남기기 위해서다). 두 번째로 고치게 하면 `_fix2`, `_full_fix2`로 저장한다.
4. 그 묶음의 검사 명령에서 파일 이름만 `_fix1.yaml`로 바꿔 돌린다. 예: `uv run python src/questions/check_candidates.py research_notes/stage3_dev/chat4/batch1_ko-ko_fix1.yaml --batch ko-ko`

   - `batch1_ko-ko.yaml` → `batch1_ko-ko_before_fix.yaml`, `batch1_ko-ko_full.md` → `batch1_ko-ko_full_before_fix.md`
   - `batch1_ko-ko_fix1.yaml` → `batch1_ko-ko.yaml`, `batch1_ko-ko_full_fix1.md` → `batch1_ko-ko_full.md`
   - **개발용:** 사용자가 통과를 알리면 Claude가 바꾼다.

## Claude에게 물어도 되는 것과 안 되는 것

| 물어도 되는 것 | 안 되는 것 |
|---|---|
| 절차, 형식, 칸의 뜻, 규칙의 해석 | 질문 문장, 정답, 근거 구절을 붙여 넣는 것 |
| 형식 검사 스크립트의 메시지 | "이 질문이 괜찮은가"처럼 내용을 판단해 달라는 것 |
| 어느 칸이 몇 개 모자라는지 | 실제 후보를 예로 드는 것 |
| 지어낸 다른 예로 "이런 경우는 어느 유형인가"를 묻는 것 | 화면을 그대로 캡처해 보여 주는 것 |

실수로 내용을 보여 줬으면 그 사실을 `DECISIONS.md`에 적고, 보여 준 질문은 최종 평가용에서 빼고 여분의 후보로 바꾼다.
